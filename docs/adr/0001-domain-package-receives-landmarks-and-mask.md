# Domain package receives landmarks + segmentation mask, not pre-built zone polygons

`packages/domain` computes zone polygons (forehead, cheeks, nose, chin — see `docs/research/redness-index.md`) itself from a platform-supplied `{ landmarks, skinMask }` pair, rather than each app (`apps/web`, `apps/mobile`) building its own zone polygons and passing those in. Both platforms standardize on MediaPipe's plain 468-point face mesh topology (web via `@mediapipe/tasks-vision`, which returns 478 including iris but only the first 468 are used; native via `react-native-fast-tflite` running the plain `face_landmark.tflite`, not the `_with_attention` variant; corrected 2026-09-11, see note below), so the landmark→zone-polygon geometry — including the exclusion polygons for eyes/brows/lips/nostrils — needs writing only once, in the pure, tested domain package, instead of twice with a risk of the two copies drifting apart.

**Correction (2026-09-11, while resolving the wire-format ticket that followed this one):** this ADR's first draft assumed both platforms produce a 478-point mesh (that wording is not preserved verbatim — this note summarizes what changed and why, rather than quoting it). Verified research found that's only true for web; the plain native `.tflite` file is 468 points (`[1,1,1,1404]` tensor) — reaching 478 on native requires the separate `face_landmark_with_attention.tflite` file and combining extra tensors for lips/eyes/iris. Since iris landmarks aren't needed for skin-zone redness analysis, the project standardizes on 468 points everywhere instead (web drops its 10 iris points) rather than adopting the more complex attention-variant path on native. The core decision above (landmarks+mask cross the boundary, domain computes zones once) is unaffected; only the point count and which native model file is used changed.

**Addendum (2026-09-11, follow-up grilling pass — the wire-format shape ticket 05 decided was never actually recorded here, despite `map.md` and ticket 05 both saying it was):** the boundary shape is `{ width, height, landmarks: {x,y,z}[468], skinMask?: Uint8Array }`, matching the internal `mediapipe-tflite` skill's `FaceCapture` type exactly. Two points beyond the point-count correction above: `z` is kept (both platforms emit it as part of their native 3-value-per-point output anyway; dropping it would be extra filtering for no benefit). `skinMask` is a pre-reduced **binary** `Uint8Array` (1 = skin), not the raw multi-class category mask — native's `selfie_segmentation` model has no multi-class output to pass through, so each platform's adapter must reduce to binary itself. The two platforms' binary masks mean different things (web's is specifically face-skin; native's is person/foreground generally, including hair/neck/clothes) — worth a code comment where `apps/mobile`'s adapter is implemented. Full reasoning: [ticket 05](../../.scratch/production-readiness/issues/05-landmark-mask-wire-format.md).

## Considered Options

- Each app computes its own zone polygons and passes pre-built polygons into `packages/domain`: rejected — duplicates non-trivial geometry across web and native, and `packages/domain`'s stated scope already includes "zones" (`AGENTS.md`).
- Native uses `face_landmark_with_attention.tflite` to reach 478 points (matching web's full output): rejected — requires combining multiple output tensors (base mesh + refined lips/eyes/iris) instead of reading one tensor, for landmark precision (iris) the product doesn't use.
