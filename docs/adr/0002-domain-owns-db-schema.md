# packages/domain owns the DB schema; Supabase migrations generate from it

`packages/domain` defines the Postgres tables for the app's persisted entities (`Photo`, `Spot`, `ZoneReading`, `RoutineEntry`, `RoutineItem` — see `CONTEXT.md`) as TypeScript, and Supabase migrations are generated from those definitions rather than hand-written SQL kept in sync by hand. This inverts Supabase's own idiomatic workflow (write SQL migrations, then `supabase gen types typescript` to generate TS types from the DB) in exchange for a single source of truth: chosen over hand-written migrations because drift risk (TS schema vs. DB columns silently diverging) was judged worse than the cost of introducing a schema-to-SQL tool (e.g. Drizzle ORM) this late in a 9-day build. Row-Level Security policies are Postgres-specific and keyed on `auth.uid()` (see `docs/research/supabase-expo-nextjs.md`) — they still need hand-written SQL alongside the generated table DDL; whether the chosen tool's RLS support fits Supabase's specific patterns was not verified before this decision and should be checked when implementation starts. Checked 2026-09-13 (ticket 03): Drizzle's `pgPolicy` + `enableRLS()` emit the policies in the generated migration too, so no hand-written SQL remains.

## Considered Options

- Domain owns only logic-level schemas (validation + types); Supabase migrations hand-written separately, not required to match 1:1: rejected — accepts drift risk to avoid a new toolchain. Dinh chose single-source-of-truth safety instead, given the schedule (2026-09-11).

**Addendum (2026-09-13, ticket 07):** one exception to "no hand-written SQL". Supabase Storage's access rules are policies on `storage.objects`, a table Supabase owns and drizzle cannot model, so the `photos` bucket's owner-folder policy is `packages/domain/drizzle/0002_photos_storage_owner_policy.sql`, created with `drizzle-kit generate --custom` (an empty, journaled migration filled in by hand). It still lives in the domain package's migration chain and is applied like the generated ones; only its body is hand-written. Any future `storage.objects` policy takes the same route.
